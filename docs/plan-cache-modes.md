# План: режимы кэша, мониторинг и лимиты

Статус: **согласовано, не реализовано**. Дата: 2026-11-22. OMP 19.1.0,
маршрут `cline-pass`.

## Задача

Не платить за систематические промахи кэша префикса и видеть, что происходит,
не читая JSONL руками. Не цель — экономить на одном холодном ходе: он стоит
15–26 центов (см. таблицу), дорого обходится накопление.

## Решения (из согласования)

| Вопрос | Решение |
|---|---|
| `session.warnCost` / `maxCost` | **Не ставим сейчас.** Наблюдаем; вернуться, когда будет 2 недели данных по `hit` и `cost` |
| Переключение режимов | **Только на запуске**: алиасы/wrapper + бейдж активного режима. `/mode` посреди сессии не делаем |
| Мониторинг | Расширение `/cache` + cache-hit в статус-строке + предупреждение при промахе |
| План | этот файл; в вики — только ссылка, когда появится реализация |

## Что уже известно (замеры, не догадки)

Цены — `omp models --json`, этот маршрут:

| Модель | input $/M | cacheRead $/M | output $/M | 500k промах | 500k из кэша |
|---|---|---|---|---|---|
| `deepseek-v4.1-flash-1017` | 0.30 | 0.006 | 1.20 | $0.150 | $0.003 |
| `deepseek-v4-pro` | 0.522 | 0.0435 | 1.044 | $0.261 | $0.022 |

Основная сессия из вики: 25.4M `cacheRead`. Из кэша — $0.15 (flash) / $1.10
(pro); всё промахом — $7.6 / $13.3. Обычный ход отправляет весь контекст, но
платный input — только некэшированный хвост; полный повтор префикса бывает при
смене модели/thinking/режима/tool-set, compaction или вытеснении записи.

Откуда числа: провайдер возвращает usage на каждый ответ
(`prompt_tokens_details.cached_tokens`, `prompt_cache_hit_tokens/miss_tokens`,
`cache_write_tokens`); ClinePass отдаёт авторитетную стоимость
(`applyProviderReportedCost`). OMP нормализует в `input`/`cacheRead`/
`cacheWrite`/`cost` и пишет в JSONL сессии и `stats.db`. Отдельных «марок
хода» провайдер не присылает; TTL/shared-cache/retention у `cline-pass` в доках
не подтверждены — опора только на `cacheRead > 0`.

Ограничения: `cacheWrite` на этом маршруте = 0, поэтому
`display.cacheMissMarker` бесполезен; порог его срабатывания не документирован.

## Этап 1: режимы на запуске

Файлы пресетов уже в `~/.omp/presets/` (`cache-safe.yml`, `quality.yml`,
`throughput.yml`), проверены прогоном. Добавить обёртку, которая:

1. выбирает пресет **до** первого сообщения: `omp-mode cache-safe` →
   `OMP_MODE=cache-safe exec omp --config ~/.omp/presets/cache-safe.yml "$@"`;
2. не меняет `~/.omp/agent/config.yml` (оверлей, как сейчас).

Алиасы: `ompc`/`ompq`/`ompt` (уже описаны в `presets/README.md`).

Бейдж: расширение `mode-badge` (~30 строк TS) читает `process.env.OMP_MODE` и
публикует `ctx.ui.setStatus("mode", name)`. В статус-строке включить сегмент
`status`:

```yaml
statusLine:
  preset: default
  rightSegments: ["session_name", "token_total", "cost", "context_pct", "status"]
```

Пустой `OMP_MODE` — статус не публикуется (обычный `omp` без бейджа).

## Этап 2: `/cache` и hit% в статус-строке

Расширение в `~/.omp/agent/extensions/` (авто-обнаружение;
альтернатива — `extensions:` в `~/.omp/agent/config.yml`). Что делает:

- на `turn_end` берёт usage последнего assistant-сообщения и считает
  `hit = cacheRead / (input + cacheRead)`, плюс `cost` хода и сумму сессии;
- публикует в статус-строку короткое `↺ 96%`;
- при `hit < 50%` после первого хода — `ctx.ui.notify(..., "warning")`:
  «кэш сломался на этом ходе» (первый ход холодный всегда, его не считаем);
- команда `/cache` печатает: активный режим (`OMP_MODE`), роли/thinking из
  эффективных настроек, hit% последнего хода и сессии, стоимость сессии.
  Ничего не меняет — только чтение.

Ничего не пишет в файлы, кроме `appendEntry` (если понадобится история), и не
вмешивается в запросы: обработчики расширения изолированы, исключение не
ломает ход.

## Перед реализацией — проверить (spikes)

1. Есть ли `usage` в payload `turn_end`; если нет — брать из `message_end`
   assistant-сообщения.
2. Обновляется ли сегмент `status` в TUI на каждом `setStatus` (и как ведёт
   себя в `--mode json`/`print`).
3. Действует ли `session.maxCost` на сабагентов (у них отдельные сессии), если
   решим включать лимит позже.
4. Загружается ли расширение из `~/.omp/agent/extensions/` без записи в
   `config.yml` (ожидается да, по `extension-loading.md`).

## Критерии приёмки

- `ompc -p 'ok'` работает, `OMP_MODE=cache-safe`, в статус-строке `cache-safe`.
- `/cache` в TUI показывает hit% и стоимость; цифры совпадают с usage в JSONL
  того же хода (сверка скриптом из вики).
- Искусственный промах (смена модели посреди сессии) даёт предупреждение.
- `omp` без обёртки и без `OMP_MODE` работает как раньше.

## Не делаем

- Переключение режима посреди сессии: это и есть холодный префикс.
- Markdown-команды вместо переключения: они не меняют настройки.
- `cacheMissMarker` на этом маршруте (`cacheWrite = 0`).
- Расчёт на TTL/1h/shared-cache у `cline-pass`, пока не подтверждены.
- Изменение `~/.omp/agent/config.yml` ради пресетов.

## Риски

- Стоимость уже отправленного запроса не отменить; лимит останавливает только
  следующий (поэтому `maxCost` — страховка, а не контроль).
- Первый ход каждой сессии и каждый сабагент холодные (4–9k prefill) — это не
  поломка, и предупреждение не должно на них срабатывать.
- Расширение видит usage только после ответа провайдера; при стриминге статус
  обновится к концу хода.
