    Оркестрация: Orca и OMP

    Orca не «крутит OMP внутри себя». Она поднимает отдельные процессы OMP в отдельных worktree и связывает их сообщениями. Внутри одного процесса живёт только OMP-слой сабагентов.

    Терминология Run — namespace и домашний inbox. Task — единица работы. Dispatch — конкретный запуск задачи у воркера. Worker — агент в своём worktree. Всё это живёт в Orca, а не в OMP.

    Три уровня

    УровеньЕдиницаКто создаётИзоляция
    Workspace / worktreegit-checkout + ветка + терминалыorca worktree createсвой каталог, свой OMP
    Supervised workerRun → Task → Dispatch → терминал агентаorca orchestration worker-startсвой worktree + отдельный процесс
    OMP-сабагентtask-вызов внутри сессиисам OMPобщий процесс, общий checkout

    Что происходит при спавне

    orca worktree create --agent omp делает новый checkout от базовой ветки, запускает omp в терминале этого каталога и передаёт промпт. Для нового запуска промпт идёт через launch journal, а расширение orca-prefill.ts кладёт его в редактор OMP через ORCA_OMP_PREFILL. В чат-режиме сообщение приходит целиком.

    Handoff — отдал и забыл

    orca worktree create --name fix-race --agent omp \
  --surface terminal --prompt "$(cat brief.md)" --json

    Результат не ждётся, исходный агент останавливается. Для «просто сделай в другой ветке».

    Supervised worker — ждём результат

    orca orchestration run-create --objective "починить гонку в keygate" --json
orca orchestration task-create --spec-file brief.md --task-title fix-race --json
orca orchestration worker-start --environment local \
  --spec-file brief.md --worktree new-child --name fix-race \
  --agent omp --model "@slow" --json
# закончить ход; Orca разбудит на worker_done / question / escalation
    --worktreeЧто будетКогда
    currentРабота в вашем checkoutТолько read-only или уверены, что файлы не пересекутся
    new-childВложенный worktree под вашимОбычный параллельный фикс
    new-top-levelНезависимый worktree от репозиторияОтдельная задача, не связанная с вашей веткой
    Spec Задача должна быть самодостаточной: цель, изменение, ограничения, что можно править, чем доказано «готово». Отдельно укажите, означает ли ненулевой exit провал или это и есть результат.

    Обмен сообщениями

    Тело сообщения не печатается в терминал воркера. Orca будит его служебной заметкой, а воркер сам забирает почту командой check.

    # координатор
orca orchestration send --to dispatch:<id> --subject "уточнение" --body-file msg.md --json

# воркер
orca orchestration check                       # FIFO-батч, помечает прочитанным
orca orchestration check --wait --timeout-ms 300000
orca orchestration check --peek --format       # посмотреть, не забирая

# ответ на вопрос
orca orchestration reply --id <message_id> --body "ответ"
    • Доставка ровно один раз: при потере ответа переиспользуйте operationId / --retry-request, а не новый запуск.
    • worker_done закрывает Task; провал никогда не помечается выполненным.
    • escalation с stopReason значит, что воркер остановился без отчёта — стеерить, перезапускать или сказать пользователю.
    • exited/lost — процесс исчез.

    Наблюдение

    orca agent list --json                 # чаты и терминалы, состояние
orca agent read <id> --json            # транскрипт, не экран
orca terminal read --terminal <h> --screen --json
orca terminal wait --terminal <h> --for tui-idle --timeout-ms 300000
orca orchestration worker-list --json
orca orchestration inbox --terminal run:<run_id> --limit 50

    tui-idle работает для OMP потому, что в сессию подключается orca-agent-status.ts через --extension. Без отчётов статуса Orca не знает, свободен ли агент, и держит почту неотданной.

    Когда что использовать

    СитуацияИнструмент
    Параллельные ветки и фиксы в разных worktreeOrca workers
    Нужен другой агент (Codex / Claude / Pi) или другая машинаOrca workers
    Долгая задача, результат позже, нужен relay на телефонOrca + relay
    Разведка по репозиторию, пять read-only скаутовOMP task
    Параллельные правки в одном репо с изоляциейOMP task + isolated: true
    Один связный рефакторингОдна сессия, без фан-аута

    Двойная оркестрация (Orca-воркер, который сам спавнит шесть OMP-сабагентов) законна, но дорога: каждый уровень умножает расход и усложняет атрибуцию ошибок.

    Подводные камни

    • Не поллить. Скрипт с check съедает почту, и Orca нечем будить координатора. Завершили ход — Orca разбудит.
    • Спящий терминал нельзя адресовать: сначала откройте его workspace.
    • Почта в живой терминал не durable: закрылся терминал — сообщение потеряно.
    • terminal send для общения с агентом запрещён: только orchestration send.
    • Стартуйте ~4 воркера одновременно, остальные — по мере возврата.
    • worker-start не проверяет, установлен ли CLI: отсутствующий бинарь вылезет как agent_readiness timeout.
    • Авторетраев нет. «Тишина» не доказывает, что процесс остановлен.
    • Если OMP показывает меню доверия или разрешений, промпт с Enter будет отклонён (agent_prompt_blocked): меню должен закрыть человек.
    • OMP практичнее держать в --surface terminal; чат — только если агент и хост это поддерживают.

    Специфика OMP

    • --model принимает не только provider/id, но и роли OMP: @slow, @smol.
    • --effort маппится на thinking OMP; требует --model.
    • Статус и prefill приходят от двух расширений Orca в ~/.omp/agent/extensions/; не удалять их.
    • orca agent installed на этой машине: pi (default), omp, cline, dsh.
    • Чтобы воркер не потерял конфиг, проектные .omp/ файлы должны быть в ветке, от которой создаётся worktree.
